Masterly.Hash — password cracking playground

Suppose an attacker steals your user table and cracks it offline, with no rate limits and no lockouts. How long would one password last under each storage scheme? This page compares the hashes Masterly.Hash 2.x writes against older and weaker options.

Everything stays in your browser. The page makes no network requests and stores nothing. You can turn off your network and it still works. Still, do not type a real password you use; try one that is like it.

Why slow hashes?

MD5, SHA-1 and SHA-512 are built to be fast. That is right for checksums and wrong for passwords: one GPU tries billions of guesses per second. Password hashes (PBKDF2, bcrypt, Argon2id) are slow on purpose and have a tunable cost. A login that takes your server about 50–250 ms costs the attacker the same work for every guess. The attacker's speed drops by a factor of a million or more.

Why memory-hard (Argon2id)?

PBKDF2 and bcrypt only cost CPU time, and GPUs and ASICs have a great deal of parallel compute. Argon2id also makes every guess fill and re-read a large block of memory: 64 MiB in the default profile 2026a. The attacker then hits the limits of memory size and bandwidth, which cost much more to scale than arithmetic does. A 24 GB GPU holds only a few hundred 64 MiB guesses in flight at once. Argon2id won the Password Hashing Competition and is specified in RFC 9106.

What salts do, and what they do not do

A salt is a unique random value stored next to each hash. It does not slow down an attack on one targeted password: the attacker reads the salt from the database and hashes guesses with it. That is why "salted SHA-512" (Masterly.Hash 1.x) is barely better than plain SHA-1 in the table.

What salts do stop is precomputation and batching. Rainbow tables become useless, and each guess tests one user instead of all of them. Without salts, one pass over a wordlist cracks every user who picked that word, and identical passwords show up as identical hashes. Masterly.Hash always uses a 16-byte random salt.

What a pepper adds

A pepper is a secret key, at least 32 bytes, that is mixed into every hash (Masterly.Hash uses HMAC-SHA256) and is kept out of the database: in an environment secret, Azure Key Vault, AWS KMS or HashiCorp Vault (the Masterly.Hash.Pepper.* packages). An attacker who has only the database dump cannot check a single guess. They would first have to brute-force a 256-bit key, which is not possible.

The protection holds only while the key stays secret. If the attacker also takes over the application server or the key store, the pepper is gone and the matching row above applies again. A pepper adds to a slow hash; it does not replace one.

Masterly.Hash upgrades 1.x hashes automatically on login

You do not need a password-reset campaign. Masterly.Hash 2.x still verifies 1.x salted SHA-512 hashes. When a user logs in successfully, it returns a fresh hash built with the current profile (Argon2id 64 MiB by default), and you store it:

// After a successful credential check:
var result = Password.Verify(password, user.PasswordHash);
if (result.IsMatch && result.Rehash is { } fresh) user.PasswordHash = fresh;

The same path moves hashes to a newer profile or a rotated pepper key. Accounts that never log in keep their old hash, so plan to expire them or wrap them in a stronger hash.

Sources and derivations

All figures are approximate, order-of-magnitude numbers for one RTX 4090-class GPU. Real speeds change with the driver, the cracking tool version, clock speeds and the attack mode. Treat each figure as roughly "within 2–3×".

  1. hashcat v6.2.6 benchmark on an RTX 4090 (Chick3nman, public gist): gist.github.com/Chick3nman/32e662a5bb63bc4f51b847bb422222fd. Mode 0 MD5 ≈ 164 GH/s (1.6×1011). Mode 100 SHA-1 ≈ 50.6 GH/s (5×1010). Mode 1700 SHA2-512 ≈ 7.5 GH/s (7×109).
  2. Masterly.Hash 1.x computes a single SHA-512 over password + random salt. Salted single-pass SHA-512 (hashcat mode 1710) runs at about raw SHA-512 speed, so this page uses ≈ 7×109 H/s.
  3. PBKDF2-HMAC-SHA512, 210,000 iterations (derived): hashcat mode 12100 benchmarks at ≈ 3.12 MH/s with 999 iterations. The cost grows linearly with the iteration count: 3.12×106 × 999 / 210,000 ≈ 1.5×104 H/s.
  4. bcrypt (derived): hashcat mode 3200 benchmarks at ≈ 184 kH/s at cost 5 (25 = 32 rounds). Each extra cost step doubles the work, so the rate is 1.84×105 / 2(cost−5). Cost 10 ≈ 5.8×103 H/s. Cost 12 ≈ 1.4×103 H/s.
  5. Argon2id (estimated): GPU speed for Argon2 is limited by memory bandwidth and capacity, and published numbers vary widely by implementation. A rough upper bound: each guess moves about 3 KiB of memory per 1 KiB block, per pass. For 64 MiB with t=3 that is ≈ 0.6 GB per guess. At ≈ 1 TB/s that allows at most ≈ 1,700 guesses/s, so this page uses ≈ 1×103 H/s. For 19 MiB with t=2 (≈ 0.12 GB per guess) the bound is ≈ 8,700/s, and this page uses ≈ 5×103 H/s. Parameters follow RFC 9106 (§4: second recommended option, 64 MiB, t=3; Masterly.Hash uses p=1) and the OWASP Password Storage Cheat Sheet (minimum Argon2id m=19 MiB, t=2, p=1; PBKDF2-HMAC-SHA512 at 210,000 iterations; bcrypt cost ≥ 10).
  6. Attacker budgets. The 8-GPU rig is 8 times the single-GPU rate, assuming perfect scaling. For the cloud budget this page assumes about $1 per GPU-hour for a 4090-class card, so $10,000 ≈ 10,000 GPU-hours ≈ 3.6×107 GPU-seconds. The page then shows the total number of guesses that budget buys, not a time.
  7. Guess estimator. This is a simplified pattern model in the spirit of zxcvbn (D. Wheeler, "zxcvbn: Low-Budget Password Strength Estimation", USENIX Security 2016). It splits the password into tokens: common password, dictionary word (assumed to sit among the top ~10,000 words), repeat, sequence, year, and leftover characters at their character-class pool size. It multiplies the token costs, applies a small ordering factor, and keeps the result only if it is lower than plain brute force. The expected time to crack is half the guesses divided by the attacker's rate.

Disclaimer. This is an educational estimate, not a security guarantee. Every figure is approximate and order-of-magnitude. Real attacks can be much faster: better wordlists, rules, leaked passwords from other sites, newer hardware. Do not type a password you really use, even though nothing leaves this page.
