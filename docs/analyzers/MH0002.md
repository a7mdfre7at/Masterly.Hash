# MH0002: Non-constant-time comparison of secrets

| Property | Value |
|----------|-------|
| Category | Security |
| Default severity | Warning |
| Code fix | Yes, for `byte[]` / `Span<byte>` `SequenceEqual` when `CryptographicOperations.FixedTimeEquals` exists and the behavior on `null` is unchanged |

## Cause

A value whose name says it is a secret is compared with an early-exit comparison:

- `==` / `!=` on strings
- `string.Equals` (static and instance), `string.Compare`, `string.CompareOrdinal`
- `Enumerable.SequenceEqual` / `MemoryExtensions.SequenceEqual` on `byte` or `char` sequences

A name matches when it contains one of the words **hash, hashed, digest, mac, hmac, signature, token, apikey, secret**
(whole words, as described in [MH0001](MH0001.md)). The rule looks through value-preserving calls such as
`Convert.ToBase64String(mac)`, `hash.AsSpan()` and `token.Trim()`.

### What does not trigger

- comparisons with `null`, `default`, `""` or `string.Empty` (`hash == null`, `token != ""`)
- numeric comparisons such as `hash.Length == 32` or `digest.Length != mac.Length`
- names where the secret word is followed by a metadata word: `hashAlgorithm`, `tokenType`, `signatureScheme`,
  `macAddress`, `macAddressBytes`, `secretName`,
  `apiKeyHeader`, `GetHashCode`, and so on
- non-word matches such as `hashtag`, `machine` and `tokenizer`
- `nameof(token)`

## Why it matters

These comparisons return as soon as they find a difference, so the time they take reveals how many leading bytes of
an attacker's guess are correct. Over many requests, an attacker can recover a valid MAC, API key or reset token byte
by byte.

## How to fix

```csharp
// Before
if (computedMac.SequenceEqual(expectedMac)) { ... }

// After
if (CryptographicOperations.FixedTimeEquals(computedMac, expectedMac)) { ... }
```

For strings, compare the decoded bytes (or the UTF-8 bytes) with `CryptographicOperations.FixedTimeEquals`. For
password hashes, use `Password.Verify`, which already compares in constant time.

The code fix applies only to byte arrays and byte spans, and only when the target framework has
`System.Security.Cryptography.CryptographicOperations` (.NET Core 2.1+ / .NET Standard 2.1+). It is not offered for
`a?.SequenceEqual(b)`.

`FixedTimeEquals` treats a `null` array as an empty span, while `Enumerable.SequenceEqual` throws on `null`. A blind
rewrite could therefore turn a failing comparison into a passing one (`null` equals `new byte[0]`, for example a
missing cached MAC against an empty header), which is an authentication bypass. For `Enumerable.SequenceEqual` the fix
is offered only when nullable flow analysis proves both operands non-null: nullable context enabled, no `!`
suppression on the operand, and a `NotNull` flow state (non-nullable parameters, results of `HashData`, values after an
`is null` check). In nullable-oblivious code, or for `byte[]?` operands, add an explicit null check and rewrite by hand:

```csharp
if (expectedMac is null || providedMac is null) return false;
return CryptographicOperations.FixedTimeEquals(expectedMac, providedMac);
```

`MemoryExtensions.SequenceEqual` (on spans) already treats `null` as empty, so its fix is always offered.
